# einvoice-total-check —— 税額が 27 セント足りない請求書が EN 16931 の公式の規則を通った。しかもそれは仕様どおりだった

ドイツでは 2027 年から事業者どうしの請求書を電子請求書で出すことになります(前年の売上が 80 万ユーロ以下なら 2028 年から。形式は ZUGFeRD / Factur-X か XRechnung)。検証の基準になるのは EN 16931 の CEN の規則で、Schematron の形で [ConnectingEurope/eInvoicing-EN16931](https://github.com/ConnectingEurope/eInvoicing-EN16931) に公開されています。その計算の規則には、見落としやすい点が 2 つあります。

- **税率ごとの税額は、1.00 近くずれていても通ります。**BR-S-09 は `|宣言した税額 - 課税標準 x 税率| < 1`、BR-CO-17 は `<= 1` を許します。EN の本文は「等しくなければならない」です。この幅は、明細ごとに税額を丸めるソフトのためにわざと入れられたものです([#370](https://github.com/ConnectingEurope/eInvoicing-EN16931/issues/370)。幅は 1 ユーロではなく、どの通貨でも `1` だと指摘されています)。[#432](https://github.com/ConnectingEurope/eInvoicing-EN16931/issues/432)(2025 年)では、64.26 に 21 % で税額 13.22 と書いた請求書 —— 正しくは 13.49 —— が検証を通り、返ってきた答えは「The rule BR-CO-17 allows for a slack of 1.」でした。2026-09-23 に読んだ規則のファイルにも、この幅は残っています
- **規則を動かすのは Java と XSLT です。**請求書を Python で出しているなら、合計を確かめるには JVM と検証器を入れるか、確かめないかのどちらかになります

`einvoice_total_check.py` は、CII の請求書の合計と税額を標準ライブラリだけで計算し直し、どの宣言額が食い違っているか、本来いくらかを出します。公式の幅が通してしまう税額は、`STRICT-VAT` として別の行に出します。

```bash
python einvoice_total_check.py invoice.xml [more.xml ...]
python einvoice_total_check.py invoice.xml --strict    # STRICT-VAT も失敗に数える
python einvoice_total_check.py invoice.xml --tsv       # 規則とファイルごとに 1 行
```

```
FAIL  invoice.xml
  FAIL      BR-CO-16  DuePayableAmount 118.99, total with VAT - paid + rounding = 119.00
PASS  other.xml
  note      STRICT-VAT  S 21%: CalculatedAmount 13.22, BasisAmount 64.26 x rate = 13.4946 (passes the official tolerance if within 1.00; not an official rule)
```

Python 標準ライブラリのみ。Java も通信も要りません。

## 何を見るか

次の 10 の計算の規則を、公式の CII の対応付け(`cii/schematron/CII/EN16931-CII-model.sch`)の式から読み直して実装しました。公式では 10 本とも `fatal` です。

| 規則 | 宣言額 | 計算し直す式 |
|---|---|---|
| BR-CO-10 | 明細の正味金額の合計 | 明細の和をセントに丸めたもの |
| BR-CO-11 / 12 | 文書全体の値引き / 追加料金の合計 | 値引き / 追加料金の和 |
| BR-CO-13 | 税抜の合計 | 明細 - 値引き + 追加料金 |
| BR-CO-14 | 税額の合計(請求書の通貨) | 税の内訳の税額の和 |
| BR-CO-15 | 税込の合計 | 税抜の合計 + 税額の合計 |
| BR-CO-16 | 支払額 | 税込の合計 - 支払済み + 端数調整(丸めも幅も無し) |
| BR-S-08 | 標準税率ごとの課税標準 | その税率の明細 + 追加料金 - 値引き |
| BR-S-09 | 標準税率ごとの税額 | 課税標準 x 税率、**幅 < 1** |
| BR-CO-17 | すべての内訳の税額 | 課税標準 x 税率、**幅 <= 1**。税率が無いか 0 なら、税額は丸めて 0 |
| `STRICT-VAT` | *公式の規則ではない* | 課税標準 x 税率をセントに丸めたもの(四捨五入・偶数丸め・+∞ 方向のどれでも可。課税標準と税額が両方とも整数なら、HUF のように整数への丸めも可) |

**終了コード:** 0 = 全部の規則が成り立つ / 1 = 規則が崩れている(`--strict` なら STRICT-VAT も)/ 2 = CII の請求書として読めない / **3 = 崩れてはいないが、見られていないものがある(UBL のファイル、または `SPLIT` の規則)。**3 は合格ではありません。

**`SPLIT` について。**公式の規則は XPath で書かれており、和の一部は 2 進の浮動小数点で、一部は 10 進で取られ、`round()` にはちょうど半分のときの決まりがあります。どの箇所でどれが効くかを分かったふりをせず、全部の規則を 3 通り(10 進で半分は +∞ 方向・10 進で半分は 0 から遠い方向・2 進の倍精度)で計算し、3 通りで結果が揃わない規則を数字つきで `SPLIT` と出します。起きるのは小数 3 桁以上の明細の金額です(`1.005` は 10 進では 100.5 セント、倍精度では 100.49999999999999)。公式の例 15 本では、割れた規則は 0 でした。

## 測ったこと

**公式のリポジトリにある CII の例の請求書 15 本**(2026-09-23 に GitHub の API で取得。15 本とも blob のハッシュが一致): **15 本とも合格**。`--strict` でも合格で、割れた規則も 0。うち 1 本は [#325](https://github.com/ConnectingEurope/eInvoicing-EN16931/issues/325) のハンガリーの請求書で、69,180 に 27 % の税額 18,679 をフォリントの整数に丸めています。整数への丸めを認めているのはこのためです。

**同じ 15 本をわざと壊したもの** —— 生成器の不具合がやりそうな形で、金額を 1 か所ずつ変えました。

| 変えたもの | 当てられた本数 | その規則で捕まえた本数 |
|---|---:|---:|
| 明細合計 +1 | 15 | 15 |
| 値引きの合計 +0.01 | 5 | 5 |
| 追加料金の合計 +0.01 | 7 | 7 |
| 税抜の合計 +0.01 | 15 | 15 |
| 税込の合計 +0.01 | 15 | 15 |
| 支払額 +0.01 | 15 | 15 |
| 標準税率の課税標準 +0.01 | 12 | 12 |
| 標準税率の税額 +2 | 12 | 12 |
| **標準税率の税額 +0.99(合計の側も揃えたもの)** | 12 | **11 本は上の公式の規則を全部通る。STRICT-VAT は 12 本とも出す** |

通らなかった 1 本はハンガリーの請求書です。もともとの端数 0.40 で幅の一部を使っていました。

**途中の自分たちの誤り。**最初の実行では、公式の例の 1 本 `CII_example7.xml`(区分 O =「課税対象外」で、税率を持たない)を BR-CO-17 で落としていました。この規則には、まさにその場合の 3 つ目の枝 —— 税率が無ければ税額は丸めて 0 —— があり、私たちは式を 600 字で切って表示していたので見ていませんでした。公式の例に当てなければ、課税対象外の正しい請求書を全部はじく検査器を出していたところです。

試験 40 本。`mutation_check.py` は検査器を 20 通りに壊し(幅を 2 に広げる・SPLIT を合格に数える・`--strict` を無視する・整数への丸めを全部に認める・読めない数を 0 に数える……)、そのたびに試験が落ちるかを確かめます。**初回に捕まえたのは 20 通りのうち 19 通り。**生き残った 1 通りは本物の穴でした —— `0,00` と書いた明細の金額(ドイツ語圏の小数点のカンマ)が、黙って和から抜けていました。いまは BR-CO-10 で落ち、試験もあります。

## やらないこと

- **公式の検証器の代わりにはなりません。**見るのは約 780 本(ほかにコード表とスキーマ)のうち計算の 10 本だけです。必須の欄・コード・日付・識別子は見ません。その上に載る国ごとの規則(XRechnung 独自の規則など)は読んでいません
- CII だけです。UBL のファイルは `UNCHECKED`(終了コード 3)で返します。ZUGFeRD / Factur-X の PDF は、先に中の XML を取り出してください
- BR-S-08 は税の要素ごとに照合します。公式の式は明細について区分と税率を別々の条件で見るので、1 つの明細が税を 2 つ持つときは結果が違いえます
- STRICT-VAT の整数への丸めは目安です。課税標準と税額が両方整数の内訳なら、通貨を問わず整数への丸めを認めます
- 当てた請求書は、公式の例と試験の中で組んだものだけです。実際の生成器が出した請求書は 1 本もありません。あなたのソフトが出す請求書に 1 度当てるほうが、上の表より多くを教えてくれます

公式の例のファイルは EUPL 1.2 で、ここには写していません。2 つの表を再現するには:

```bash
git clone --depth 1 https://github.com/ConnectingEurope/eInvoicing-EN16931
python einvoice_total_check.py eInvoicing-EN16931/cii/examples/*.xml --strict
python break_examples.py eInvoicing-EN16931/cii/examples
python -m unittest test_einvoice_total_check -v
python mutation_check.py
```
