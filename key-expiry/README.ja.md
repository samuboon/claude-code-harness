# key-expiry — この端末が信頼している根証明書 48 枚のうち、10 枚は既に期限切れだった

先にこれを走らせてください。OS が既に持っている証明書だけを読み、それ以外は何も見ません。

```bash
python key-expiry/trust_store_demo.py
```

このリポジトリを作っている端末での実測(2026-09-16):

```
48 certificates in the Windows ROOT store, read on 2026-09-16
  already expired : 10  (oldest by 9757 days)
  expiring in 90  : 0
  unreadable here : 0
  soonest still valid: 119 days
```

**期限切れの根証明書は、端末の穴ではありません。**`notAfter` を過ぎた証明書は単に何も検証できないだけで、古い根を残しておくのは意図的な運用です。分かったことはもっと狭く、そして質が悪い —— **その日付はずっと平文でディスクの上にあり、誰も読んでいなかった。**この道具がするのはそれだけです。

---

## 何を読むか

自分の死ぬ日を自分の中に持っている資格情報は、2 種類だけです。

| 種類 | 日付のある場所 | 手元で読めるか |
|---|---|---|
| **JSON Web Token** | ペイロードの `exp` クレーム | 読める |
| **X.509 証明書**(PEM) | Validity の `notAfter` | 読める |
| 中身の無い文字列の鍵 —— GitHub の個人アクセストークン、AWS のアクセスキー | **どこにも無い。鍵の中に書かれていない** | **読めない。手元のどんな道具にも日付は出せない** |

3 行目が正直なところで、この頁が「あなたの鍵の期限が分かります」と書けない理由です。分かるのは **2 種類だけ**で、残りについては何も言いません —— 発行元に問い合わせない限り言えることが無く、この道具は通信をしないからです。

```bash
python key-expiry/key_expiry.py .                      # 木の全体
python key-expiry/key_expiry.py ~/.kube --within 60     # 窓を広げる
python key-expiry/key_expiry.py . --format paste        # 残り日数だけ
```

```
path                     line  kind   expires               days_left  note
config/agent.token       1     jwt    2026-02-01T00:00:00Z  31         219 bytes
certs/internal.pem       1     x509   2026-04-01T00:00:00Z  90         1436 bytes
```

**終了コード**: `0` = 窓の中に切れるものが無い / `1` = ある(または既に切れている)/ `2` = **検査が行われなかった**(対象が無い・1 ファイルも読めなかった)。打ち間違えたパスに緑の印を出してはいけない、という規則は同じリポジトリの [`leak-scan/`](../leak-scan/) から引き継いだものです。

## `--format paste` —— なぜファイル名の出ない出力形式があるのか

この手の数字が共有されないのは、関心が無いからではありません。期限の検査器の自然な出力は **自分の端末のパスの一覧**であり、自分のディレクトリ構成を公開の場に貼る人はいないからです。

```
# key-expiry 0.1.0: 48 credential(s) carry a date, 29 expire within 3650 days
x509	-9757
x509	-524
x509	119
```

種類と残り日数だけ。パスもファイル名もホスト名も出ません。そして**どの形式でも、資格情報そのものは絶対に出しません**。50 個の試験のうち 1 つは、3 つの形式すべてで標準出力・標準エラーにトークンが現れないことを検査します —— 秘密を CI のログに書き出す検査器は、漏れを見つけたのではなく漏れを移しただけだからです。

**走らせたら、この塊を [Issue の雛形](https://github.com/samuboon/claude-code-harness/issues/new?template=expiry-report.yml)に貼ってください。**(2026-09-17 まで、この文は「雛形を置いてあります」と書くだけで、その雛形は木の中のどこからもリンクされていませんでした。)知りたいのは分布の形 —— **気づかないまま既に切れたものを抱えている人がどのくらい居るのか** —— で、1 台の端末の証明書置き場は分布ではありません。

## これで捕まえられないもの(実際にこちらを止めたものを含む)

**この道具は、こちらが実際に踏んだ事故を捕まえられません。**2026-09-15、このリポジトリからの push が落ちました。

```
refusing to allow a Personal Access Token to create or update workflow
.github/workflows/leak-scan.yml without workflow scope
```

この鍵は切れていませんでした。**権限が 1 つ足りなかった**のです。権限は日付ではなく、鍵の中に書かれておらず、手元では一切読めません。気づき方は誰もが気づくのと同じ、仕事が止まったときでした。このリポジトリの CI の定義がいまも `.github/` ではなく [`leak-scan/example-workflow.yml`](../leak-scan/example-workflow.yml) に置いてあるのは、その傷跡です。

つまり **日付の検査器が覆うのは、資格情報の失敗のうち「前もって自分から名乗るもの」だけ**です。権限・失効・更新漏れ・発行元が止めた鍵は、どれもここには入っていません。その全部が要るなら、発行元の API と口座と通信が要り、それは別の脅威モデルを持つ別の道具になります。

ほかに扱わないもの: PEM に包まれていない DER 単体 / PKCS#12・JKS の鍵倉 / SSH 証明書 / Kerberos のチケット / 暗号化されたファイルの中身 / 相手のホストがいま出している証明書(接続が要る)。8 MB を超えるファイルは飛ばし、**飛ばした数を出力に書きます**(黙って通しません)。

## 検査

| 何を | 数 |
|---|---:|
| 試験(`python key-expiry/test_key_expiry.py`) | **50** |
| 試験が捕まえなければならない、わざとの破壊(`python key-expiry/mutation_check.py`) | **16 / 16** |
| 実物の証明書を解析し、OpenSSL 自身の `notAfter` と突き合わせた結果 | **48 / 48 が一致** |
| 実物の証明書 48 枚・74 KB の束を走査する時間 | **2.2 ms** |
| 依存 | **0** |

試験の数より、突き合わせのほうが重要です。試験の証明書は `test_key_expiry.py` の中でタグ単位に組み立てたもので、**手で作った標本は、解析器が持っている誤解をそのまま共有します**。そこで解析器を、この端末が信頼している証明書すべてに当て、`ssl` 自身の復号を正解として比べました。**48 枚すべてが秒まで一致。**

**そして、このリポジトリ自身に当てると何も出ません**(69 ファイルを読んで `0 dated credential(s)`)。資格情報が無いので正しいのですが、実演としては最も役に立たない結果です。この頁が証明書置き場から始まるのはそのためです。

破壊の一覧は、上の数字を信じる前に読む価値があります —— `notAfter` ではなく `notBefore` を報告する / 2 桁の年をすべて `20xx` と読む(RFC 5280 は `50`〜`99` を `19xx` と定めており、そのままだと 1998 年の証明書が「2098 年まで有効」になる)/ BER の不定長を受け入れる / `"exp": true` を 1970 年として通す。16 個のうち M5 は**エラーの文面しか変えません**。一覧にはそう書いてあります(捕まえていないものを捕まえたことにしない)。

## CI で使う

[`example-workflow.yml`](example-workflow.yml) は、木の中に 30 日以内に切れるものがあればビルドを落とします。`.github/workflows/` に写して使ってください。ここに置いてある理由は上の傷跡のとおりです。
