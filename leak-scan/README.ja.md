# leak-scan —— 未追跡のバイナリまで読む公開前検査(そこに隠れていたので)

このリポジトリを公開する前日、`tools/__pycache__/` の `.pyc` 3 本に、開発機の Windows ユーザー名とプロジェクトの内部名を含む絶対パスが入っていることが分かりました。push の直前で捕まえました。**危うく見逃した理由が、そのままこの道具の設計です。**

- **`.pyc` は既定で git に追跡されません。**除外の指定はどこにも要らず、`git status` にも差分にも一度も現れませんでした
- **中身はバイナリです。**公開前に走らせていた文字列の検査でも中は見えませんでした
- **つまり 2 つの計器が同じ死角を共有していました。**互いに相手が見ているはずだと思っていたのが誤りです

そこで `leak_scan.py` は、**git の索引ではなくディレクトリを歩き**、すべてのファイルをバイト列として開き、探す語を **UTF-8 と UTF-16LE の両方**で照合します。後者は、文字列が成果物に埋め込まれたときに実際に取る形です。

標準ライブラリのみ。通信しません。**試験 37 本・わざと壊した 16 通りをすべて捕捉。**

---

## Action として使う

```yaml
- uses: actions/checkout@v4
- uses: samuboon/claude-code-harness@main
  with:
    path: .
    patterns: .github/my-identifiers.txt   # 任意
```

| 入力 | 既定 | 何をするか |
|---|---|---|
| `path` | `.` | 走査する場所。 |
| `patterns` | *(空)* | 自分の識別子を 1 行 1 語([`patterns.example.txt`](patterns.example.txt))。空なら鍵だけを見ます。**ファイル名を指定して、それが無い・空のときは失敗します**(識別子なしで静かに走って合格するのを防ぐため)。 |
| `allow` | *(空)* | 例外を `相対パス\|語` で 1 行ずつ。`*\|語` はどこでも許します。 |
| `exclude` | `.git` | 読み飛ばす接頭辞をカンマ区切りで。 |
| `fail-on` | `any` | `none` なら報告だけしてジョブを落としません。 |

出力は `hits`(件数)。終了コードは **0** 検出なし / **1** 検出あり / **2** 走査が成立しなかった。

## スクリプトとして使う

```bash
python3 leak_scan.py .
python3 leak_scan.py . --patterns my-identifiers.txt --format github
```

## 効いている 3 つの規則

**1. 1 件も読まなかった走査は合格ではありません。**読んだファイルが 0 なら終了コードは 0 ではなく **2** です。これで防ぐのは静かな失敗です —— 経路を打ち間違えた、空のディレクトリを見た、そして誰も見ていない木に緑の印が付く。

**2. 見つけたものは伏せて報告します。**

```
  - tools/__pycache__/build.cpython-313.pyc:1 | home path | C:***********
```

公開リポジトリの CI ログは公開です。見つけたものをログにそのまま出す検査は、漏れを捕まえたのではなく移しただけです。

**3. 接頭辞が一致しても鍵とは限りません。**`ghp_` や `-----BEGIN ... PRIVATE KEY-----` は、説明文にもパターン一覧にも、このファイルにも出てきます。接頭辞は鍵本体の文字が所定の数だけ続いたときに、PEM の見出しは base64 が続いたときにだけ数えます。このリポジトリを clone した直後の状態での実測(2026-09-15・58 ファイル):

| 規則 | 検出 | うち本物 |
|---|---:|---:|
| 接頭辞の形状検査なし | 33 | 0 |
| PEM の形状検査なし | 5 | 0 |
| **出荷した状態** | **0** | —— |

**自分自身を走査するのに例外リストが 1 行も要りません。ここが最後の 1 時間の主題でした。**前の版は自分の試験ファイルに 8 件出していましたが、直し方は例外ファイルではなく、試験用の値を組み立て式(`"password" + "="`)にすることでした。**要らずに済む例外リストのほうが、保守する例外リストより強い。**

識別子にも同じ問題があります。短い名前は長い語の内側に一致するので、語境界を見ます。**カタカナの境界は別に見ます** —— 日本語は分かち書きしないため、境界を見ない 3 文字の名前が**1 つの文書で 38 件の誤検知**を出したからです。UTF-16LE の側では境界を見ません(前後のバイトが手がかりにならないため)。

## この道具ができないこと

がっかりされる前に書いておきます。

- **実運用で本物の鍵を捕まえたことはありません。**きっかけはユーザー名とプロジェクト名の 1 件で、鍵の規則のほうは「この種の道具なら持っているはず」の内容であり、事故から学んだものではありません。鍵の側は未実証として扱ってください
- **形状検査は UTF-8 の形しか読みません。**1 文字 2 バイトでバイナリに入った鍵は、検索では見つかったあと `_key_shaped` で落とされます。つまりこの道具の存在理由である UTF-16 対応は、**識別子については本当で、鍵については効いていません。**既知・未修正で、次に直す 1 番目です
- **専用のシークレットスキャナの代わりにはなりません。**接頭辞 14 種・代入名 10 種は、GitHub secret scanning や `gitleaks`・`trufflehog` に比べれば短い一覧です(ただしそれらは、あなたの未追跡の `.pyc` を読みません)。両方走らせてください
- **履歴を読みません。**いまディスクにあるものだけを見ます。commit 済みで後から消した秘密は見えません
- **エントロピー判定がありません。**知らない名前の下にある 40 文字の乱数列は素通りします
- **規模に対する速度は未検証です。**すべての規則をすべてのファイルに当てており、これまで走らせた最大の木はこのリポジトリ(58 ファイル。1 秒かかりません)です。`node_modules/` のあるリポジトリに向けたことは一度もありません
