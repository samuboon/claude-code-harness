# idle-day-forecast —— チームが「取れる課題」を切らす日はいつか。Jira Cloud では、Jira 自身の履歴検索が 2020〜21 年に閉じた課題 4 件を 2026 年じゅう「未着手」と答えた

カンバンで回すチームは、取れる課題が無くなったことにその朝気づきます。「準備済み・担当なし・止められていない」課題の数は毎日ボードに出ていますが、誰もその推移を残しておらず、Jira にもその欄はありません。このフォルダは、その数を**過去の毎日について**各課題の変更履歴から組み立て直し、最近の減り方のままならいつ 0 になるかを出します。

```bash
python fetch_jira.py --base https://your-site.atlassian.net --api 3 --jql "project = TEAM" \
    --since 2025-09-23 -o team.json          # GET だけ。JIRA_EMAIL / JIRA_API_TOKEN は環境変数から
python idle_day_forecast.py team.json --ready "Ready,Selected for Development"
python idle_day_forecast.py team.json --backtest          # 1 年分の週ごとの予報を再生して採点
python idle_day_forecast.py team.json --fail-within 10    # 10 日以内に来るなら終了コード 1(定期実行向け)
python crosscheck.py team.json --every 30                 # 組み立て直した日を Jira 自身の WAS 検索と突き合わせる
```

出力の例(公開の Apache Jira・YUNIKORN):

```
pickable now: 67  (YUNIKORN-111, YUNIKORN-1185, ...)
last 28 days: 14 became pickable, 43 stopped being pickable -> the count fell 1.04 a day
forecast: pickable reaches 0 around 2026-11-27 (in 65 days; fastest week -> 2026-10-21, slowest week -> 2027-02-27)
history 2025-09-23 .. 2026-09-23: 0 idle days
```

Python 標準ライブラリのみ。`idle_day_forecast.py` は通信しません。`fetch_jira.py` と `crosscheck.py` は GET しか送りません。

---

## 「取れる」の定義

その日の終わり(`--tz`。既定は UTC)に、次を全部満たす課題を数えます。

- その時点でキューにある(作られている。別のプロジェクトから移された課題は移された時点から)
- 状態が「準備済み」 —— 既定は To Do の分類の状態すべて。`--ready` で名指しもできる
- 担当者がいない(作った時点で担当を付けるチームは `--ignore-assignee`)
- **is blocked by** で繋がった課題が、その時点で全部 Done の分類にある —— 阻む側の変更履歴も読むので、開き直された阻害元はまた阻む
- `--start-field` で開始日を取ってきたなら、それが未来でない

予報はモデルではなく算術です: いまの数 ÷ 直近 `--window` 日(28 日)に 1 日あたりいくつ減ったか。幅は、その期間の中でいちばん速かった週といちばん遅かった週から出します。横ばい・増加のときは日付でなく「0 にならない」と出します。

## 推測せずに断る(終了コード 2)

欠けた履歴から作った予報は、正しい予報と見分けがつきません。だから次のときは止まって、理由を言います。

- 検索が報告した件数より少なく返った / 変更履歴が途中で切れている
- 履歴の状態名がサイトに無い(改名)、または分類の違う状態が同じ名前を使っている —— `--status-map "旧名=done"` で解決
- 履歴を辿っても今の状態に着かない(記録の無い状態・担当者の変更)
- 取ってきていない課題に阻まれている(いた)—— 自分のアカウントで見えない課題も含む。`--unreadable-blockers blocking|ignore` で扱いを明示すれば、そう出力に書いて進む
- `--ready` にサイトに無い状態名がある / 履歴が期間より短い

準備済みの列を持つ Jira Cloud のプロジェクトで試した 1 件(Red Hat の COST・匿名)は断られました: 読めない阻害元 27 件、サイトの状態一覧に無い状態名 `M8` / `M9`、記録なしで担当者が外れた課題 2 件。

## Jira 自身の履歴検索と突き合わせた

`crosscheck.py` は、選んだ日ごとに「その日 **ON** 準備済みの状態 **WAS**・担当者が空 **WAS**」の課題を Jira に聞き、組み立て直した日の課題の番号と比べます。`WAS ... ON` はその日のどの瞬間でも当てはまれば拾い、組み立て直しは日の終わりを見るので、その日のうちに変わった課題は別に数え、食い違いに入れません。阻害は両側とも外します(JQL にはリンクの履歴が無い)。

2026-09-23 に匿名で、`--since 2025-09-23`、30 日おきに 1 日:

| サイト | プロジェクト | 比べた日 | 組み立てた課題×日 | Jira と一致 | Jira だけ・その日に変化 | 食い違い |
|---|---:|---:|---:|---:|---:|---:|
| issues.apache.org(Data Center・API v2) | 10 | 130 | 9,907 | **9,907** | 55 | **0** |
| issues.redhat.com(Cloud・API v3)の WTO | 1 | 13 | 182 | 114 | 0 | 下の 3 つの挙動を除いて 0 |

Apache の 10 本: CASSANALYTICS・CASSSIDECAR・CELEBORN・OPENNLP・RATIS・SYNCOPE・TOBAGO・UNOMI・WW・YUNIKORN。

**Jira Cloud では、間違っていたのは Jira の履歴検索の側でした。**3 通りあり、関わった課題は全部読みました。

1. **`status WAS "Open"` が、2021 年からずっと Open の課題に 0 件を返した**(WTO-108。状態の変更は一度も無い)。同じ状態を ID で聞く `status WAS 1` は返した。ワークフローの多いサイトには Open という名前の状態がいくつもあり、名前はそのうち 1 つに解決される。`crosscheck.py` は ID で聞く
2. **`assignee WAS EMPTY` は、作られてからずっと担当者のいない課題を 1 件も拾わなかった** —— 182 のうち 68。例: WTO-81 は 2021 年に担当なしで作られ、2026-08-10 に初めて担当が付いたが、`assignee WAS EMPTY` はどの日にも当たらなかった。担当が一度「外された」課題(WTO-108)は当たった。出力では「unassigned since created」として別に数える
3. **2020〜21 年に閉じた課題 4 件(本人の変更履歴による)が、2025〜26 年のどの日にも「Open・担当なし」として返った**(WTO-5・WTO-7・WTO-25・WTO-82)。4 件とも 2022-12-19 に「Workflow」の変更がある。毎回「not in file」として出す

Jira Cloud で `WAS` 検索を履歴に使っているなら(スプリントの報告・監査・SLA)、1 と 2 は自分のサイトで確かめる価値があります。

## 予報そのものは、本当に切れた日で一度も試せていない

**上の 11 本のキューは、1 年のあいだ一度も 0 になりませんでした。**オープンソースのプロジェクトは担当なしの長い積み残しを抱え、Red Hat の方も 9〜15 件を保っていました。だから過去の再生(`--backtest`: 毎週、その前の 28 日だけで予報し、続く 42 日と照らす)が採点できたのは「切れない、と言って切れなかった」だけで、キューごとに 43 回中 43 回 —— 「いつも切れないと言う」でも同じ点です。本当に切れた日について、当たったことも外れたこともまだありません。この道具の相手 —— チームが空にする小さな準備済みの列 —— は非公開のサイトにあります。**そういうキューで `--backtest` を回すと出る表が、この README に欠けている数字です。**

限界がはっきり見える例: Apache の DISPATCH は 2026-04-16 に、担当なしの未着手 201 件が同じ日に閉じられて 0 になりました。その前の週ごとの予報は「0 にならない」で、再生はそれを `missed` と数えます。減り方からは見えません。

## 試験

試験 42 本(`python -m unittest test_idle_day_forecast`)。作った変更履歴で: 状態・担当者・リンク・別プロジェクトからの移動・開き直された阻害元・開始日・時間帯の組み立て、断る条件の全部、予報の算術、再生の採点。`mutation_check.py` は予報器を 23 通りに壊し(担当のいる課題を空きと数える・阻害元を今日の状態で見る・リンクを逆に巻き戻す・日数を切り捨てる・空振りを正解と数える…)、そのたびに試験が落ちることを確かめます。**初回は 22 通り中 21 通り。**生き残ったのは「予報した当日から切れた日を探す」壊し方で、再生はすでに切れている日を飛ばすので、その差に一度も届きません。穴ではなかったので、穴になる壊し方(切った日でなく最終日から予報する = 未来を見る)に差し替えました。別プロジェクトからの移動の規則と一緒に 23 通り目を足し、いまは 23 通り中 23 通り。`fetch_jira.py` と `crosscheck.py` には通信なしの試験がありません。上の表がその試験です。

## しないこと

- 自分で書いた JQL は「今」で評価します。ラベル・コンポーネント・修正版の変更で JQL に入った/出た課題は、今の所属で数えます。プロジェクト間の移動だけは変更履歴から読みます
- 開始日は今の値で、履歴ではありません
- 1 チーム・1 キュー。誰が休みか、何人で引くかは知りません
