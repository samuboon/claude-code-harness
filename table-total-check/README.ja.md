# table-total-check —— Llama 2 のモデルカードは、3 つのモデルの下に 4 つ分の合計を載せている

`meta-llama/llama` の MODEL_CARD.md にある CO2 の表は、Llama 2 の 7B・13B・70B の 3 行と、
**Total** 行の 3,311,616 GPU 時間・539.00 tCO2eq でできています。3 行を足すと 2,273,280 と 385.08 です。
Llama 2 の論文に載っている同じ表には 4 行目があり、**34B: 1,038,336 GPU 時間・153.90 tCO2eq** —— ちょうど差の分です。
カードはその行を落として合計だけ残し、`microsoft/Llama-2-Onnx` はそのカードを写しています。

読んでいる表を足し直す人はいません。`**Total**` の行は太字で、合計のある場所にあり、そのまま信じられます。
`airbnb/mavericks` のサンプルの README では、`mvp-clean` の列が 0 + 2,777 + 608 なのに Total は 2,385 です(足すと 3,385)。
`eshu-hq/eshu` の設計文書は 64 個のディレクトリの下に 368 / 713 と書いていますが、足すと 370 / 714 になります。

`table_total_check.py` はそれを足し直します。ファイルの中の Markdown の表から、Total / Subtotal / Grand total /
合計 / 小計 … の行、Total という見出しの列、合計のある表の割合の列を見つけ、一通りにしか読めない数だけで計算し直して、
合わないものを並べます。

```bash
python table_total_check.py README.md
python table_total_check.py docs/              # 下にある .md / .markdown / .mdx を全部
python table_total_check.py docs/ --why        # 判定しなかったセルとその理由も出す
python table_total_check.py docs/ --json
```

上の 3 つのリポジトリの今日の `main`(2026-09-24)で:

```
$ python table_total_check.py llama/MODEL_CARD.md
MODEL_CARD.md:50: error TOTAL  "Time (GPU hours)", Total row: the total says 3,311,616; the 3 rows above add up to 2,273,280 (+1,038,336)
MODEL_CARD.md:50: error TOTAL  "Carbon Emitted(tCO 2 eq)", Total row: the total says 539.00; the 3 rows above add up to 385.08 (+153.92)

$ python table_total_check.py mavericks/sample-todo/README.md
sample-todo/README.md:16: error TOTAL  "mvp-clean", Total row: the total says 2,385; the 3 rows above add up to 3,385 (-1,000)
```

(385.08 + 153.90 = 538.98 で、各行が小数 2 桁で丸めてあることを考えると、表の 539.00 と合っています。)

Python の標準ライブラリだけで動きます。ファイルを読むだけで、何も実行せず、書かず、送りません
(GitHub から読むのは下の `replay_fixes.py` だけです)。誤りがあれば終了コード 1、無ければ 0 です。

## 何を出すか

| 記号 | 重さ | 意味 |
|---|---|---|
| `TOTAL` | error | Total / Sum / Grand total / Subtotal / 合計 / 小計 / 計 … の行が、上の行の和と合わない(合計の行が表の先頭に 1 つだけあるときは下の行と比べる)。小計を二重に足さない —— 総計は明細の和でも小計の和でもよい |
| `TOTAL?` | warning | 同じだが、空欄(`—` `-` `n/a`)の行があり、それが差かもしれない |
| `ROWTOTAL` | error | Total という見出しの列が、隣の列の和と合わない行。どの列を足すかは決め打ちせず、表の大半の行が合う隣の数の列の並びを表から探す。合う行が 2 つ未満なら何も判定しない |
| `SHARE` | error | 合計のある表の割合の列で、大半の行は「件数 ÷ 合計」なのに、その行だけ違う |

**ぴったり比べるもの:** 整数とお金(`$10.00 + $5.50` は `$15.50` で、`$15.49` ではない)。
**丸めを許すもの:** 小数・割合・計測値(`ms` `MB` `h` …)—— 小数 1 桁で書いた n 個の和は n × 0.05 までずれうる ——
と、全部が 000 で終わる整数(最後の 0 でない桁で丸めたと読む。OpenAI の evals の README は 19,850,000 + 80,000 を
19,940,000 と書いている。有効数字 3 桁であって誤りではない)。

**和でなくてよいもの:** 平均・中央値・最大・最小、別の列で重みを付けた平均(Passed / Run の下の合格率)になっている合計。
足すと 100 % を超える割合の列の合計(小計の下の正解率)は「割合ではなく率」として判定しない。

**合計の行と読むもの:** ラベルがその語であること(太字・コロン・括弧は許す。`**Total (16 Agents)**`、`合計(税込)`)。
`Total time` は合計の行ではない。`Batch 1 Subtotal` は小計。`COMPONENTS MERCHANDISE TOTAL` は「名前付きの合計」で、
すぐ上の行の和と合えば総計の中でそれらの代わりになり、合わなければそれ自体が 1 行の明細になる
(部品表の「PCB merchandise total」は値段であって和ではない)。Average / Avg / Mean / Median / Max / Min で始まる行は足さない。

**推測しないもの(判定しなかった数として数え、`--why` で並べる):** 数の中に混ざった文字(`3 (est.)`)、`~120`、`100+`、
打ち消し線の値、単位の混在(`900 KB` と `1.2 MB`)、`...` の行(行が省かれている)、整数の中の `1.429`
(ドットで区切った 1,429 か小数か)、1 つの数でない合計のセル(`$1,319.81 PC only / $1,459.80 with monitor`)。
Year / Version / Rank / # / ID / Date の列と、ラベルの列より左の列は、量ではなく名前として扱います。

**読めるもの:** GitHub の表(パイプ区切り)、`1,234.5` `1 234` `1.234,5`(列が小数にカンマを使うとき)、
`(20)` を −20、`$` `€` `£` `¥` `₹` と通貨コード(`IDR1,194,606`、`94.22 USD`)、`%`、セルの中のリンクとコード、`\|`。
コードブロックと HTML のコメントは読み飛ばします。HTML の `<table>`・reStructuredText・AsciiDoc は読みません。

CI での使い方は [README.md](README.md#in-ci) にあります(私たちは GitHub 上ではまだ動かしていません)。

## 測ったこと

以下は全部 `replay_fixes.py` で再現できます。検査器の第 1 版は実物の表を 1 つも読む前に凍結し、
どの組も**調整の前に** 2 つに分け、取っておいた半分は凍結した版で先に走らせました。

### 1. 合計を直した公開コミット

GitHub のコミット検索 38 通り(`fix total`、`correct totals`、`fix table arithmetic`、`does not add up` …。
一覧は `QUERIES`)で **4,566 本**。検査器を走らせる前に、差分とファイルだけから、合計**だけ**を直したもの ——
Total の行か列の数だけが変わり、足される側の行は変わっていない。つまり直す前の合計は作りから誤り —— は **6 本**でした。
「fix total」の大半はコードの修正です。コミットの ID で分けて:

| | 凍結した第 1 版 | 最終版 |
|---|---|---|
| 取っておいた 3 本 | 捕捉 1・部分 1・取りこぼし 1 | 同じ |
| 調整に使った 3 本 | 部分 1・取りこぼし 2 | 捕捉 1・部分 1・警告 1 |

- **捕捉** —— `ernestngenest/nez-harness`: 13 行で 131 のスキル数を 128 と書いていた。直す前に印が付き、直した後に消えた
- **部分** —— `Juwan-Hwang/moon-certified`: 直す前(3,291)も後(3,365)も印が付く。111 行の和はどちらも 1,481 で、
  合計がほかに何を数えているのかはファイルに書かれていない。`abhinay-sambherao/HeatScanAI`: 修正で時間の合計が 443 から 408 に
  なったが、33 行を足すと 406(手でも足し直した)
- **取りこぼし** —— `clankanoid/gaming-pc-build-2026`: 合計のセルが文(`$1,319.81 PC only / $1,459.80 with monitor`)。
  判定しないのは設計どおり
- 調整側から学んだのは、1 行だけの合計(以前は飛ばしていた)と通貨コード(`IDR1,194,606`)。**警告**のまま残った 1 本は空欄の行が 4 つある

6 本は少ない数です。検索で取れるのがこれだけでした。

### 2. 行と合計を一緒に変えたコミット

同じ検索から、合計のある表を行と一緒に書き換えたコミットが **61 本**。表が誤っていたとは誰も言っていないので、
コミット後の印は誤報か、コミットが残した誤りのどちらかです。全部を手で読みました。

| | 凍結した第 1 版 | 最終版 |
|---|---|---|
| 取っておいた 30 本 | 印 7: **本物 3・誤報 4** | 印 3: **本物 3・誤報 0** |
| 調整に使った 31 本 | 印 3: 本物 0・誤報 3(本物 1 を見逃し) | 印 2: **本物 2・誤報 0** |

本物 5 件(どれも手で足し直した): `cloudshare360/aws-cloud-engineer-with-nodejs`(講座の時間 83.0。9 節を足すと 84.0)、
`eshu-hq/eshu`(368 / 713。足すと 370 / 714)、`JasonMomanyi/EO-AI_Crop_Intelligence_Platform`(ESA の資金 47,000。
5 つの作業を足すと 47,500)、`Rabieulawal/alarmpcb` の 2 件(商品合計が上の部品の和になっていない部品表、その後の版では総計の数量 251 に対して 250)。

第 1 版の誤報と、何を変えたか: 整数の中の `1.429` を小数と読んだ(同じプロジェクトの 3 本。いまは判定しない)、
中国語の 小计 の行の下の正解率を割合として足した(いまは「割合ではなく率」)、`Batch 1 Subtotal` と
`COMPONENTS MERCHANDISE TOTAL` を合計と読めず、総計が全部を二重に数えた(上の名前付きの合計)。
第 1 版が見逃した本物は EO-AI の 47,000 で、ほかの 2 つの合計の差(53,000 − 6,000)として「説明」してしまっていました。
その説明と隣の「比」の説明は外しました。正直な場合は重み付きの平均でどちらも拾えます。

### 3. よく知られたリポジトリの今日のファイル

GitHub のコード検索で、30 の組織(microsoft・google・facebook・apache・kubernetes・rust-lang・aws・grafana・openai・
huggingface・pytorch・JetBrains・airbnb・uber …)の Markdown から `Total` を含むものを **2,787 ファイル**。
何も読む前に、リポジトリとパスのハッシュで半分に分けました。合計のある表を持つのは **63 ファイル**です。

| | 凍結した第 1 版 | 最終版 |
|---|---|---|
| 取っておいた半分(1,362 ファイル・合計あり 34) | error 4: **本物 3・誤報 1**、warning 3 はすべて誤報 | error 3: **本物 3**、warning 0 |
| 調整に使った半分(1,425 ファイル・合計あり 29) | error 9・warning 2 | error 3: **本物 3**、warning 0 |

本物: Llama 2 のカード(2 列。写しも)、mavericks の `mvp-clean`、`JetBrains/intellij-community` の python-lsp-core の
README の時間の表(3,000 + 557 の手順に 4,010 ms、1,789 の手順 1 つの下に 1,200 ms)、`uber/tango` のノードあたりバイト数の列
(18.5。8 列を足すと 19.40 —— HASH で 8.00 B/node になるノード数で 52.25 MB を割っても 19.4)。
第 1 版の誤報は、OpenAI の丸めたトークン数(上)と、pytorch/executorch の `...` の行のある表(判定を控えずに警告していた)。

2,787 ファイル全体で、最終版は **238 の和を足し直し、227 が合い、6 が合わず、5 は和ではなかった**(平均・最大)。
判定しなかったのは **39**。多いのは、隣に数の列が無い Total の列(14)と、1 つの数でない合計のセル(12)です。

**測っていないこと:** 誰も直していない表での取りこぼしの率。63 ファイルは「在るもの」で、誤りの数が分かっている見本ではありません。
文章で書いた合計(「合計は 42」)は読みません。

### 試験

`python -m unittest test_table_total_check` —— 57 本。いくつかは教えてくれた公開ファイルの名前が付いています。
