# normal-y-check —— 無料で配ったノーマルマップ 11 枚のうち 10 枚が上下逆で、ファイルのどこにもそう書いていなかった

ノーマルマップの PNG には、緑のチャンネルがどちら向きかを書く欄がありません。流儀は 2 つあり、
違うのはその符号だけです。**Y+**(「OpenGL 形式」と呼ばれることが多い)と **Y−**(「DirectX 形式」)。
Unity のマニュアルは自分の側をはっきり書いています ——「Unity uses Y+ normal maps, sometimes known
as OpenGL format.」([出典](https://docs.unity3d.com/Manual/StandardShaderMaterialParameterNormalMap.html)、
2026-09-17 に確認)。逆の形式のマップを読み込んでも、何も言われません。取り込めて、描画もされて、
上から光を当てた凸がすべて凹に見えるだけです。

**私たちはまさにそれを配りました。**2026-09-13 に BOOTH で無料の布地テクスチャを公開し、その
ノーマルマップ 11 枚のうち 10 枚が Y− でした。気づいたのは 4 日後で、しかもマップを見て気づいた
のではありません。別の道具を書いていて、そのコードの符号を Unity のマニュアルと突き合わせたとき、
布地の生成器が逆向きに書かれていることに気づきました。残る 1 枚(ストライプ)が無事だったのは
偶然です —— 凹凸が一方向にしか変わらないので、緑が一様に 128 だったのです。

マップを目で見ても捕まらなかったはずです。畝が溝に描かれても、布地は布地に見えます。
`normal_y_check.py` は、この問いを画素から答えます。

```bash
python normal_y_check.py path/to/maps               # PNG 1 枚につき 1 行
python normal_y_check.py pack/ --expect y+          # 逆と判定されたマップがあれば終了コード 1
python normal_y_check.py pack/ --tsv                # タブ区切り。1 ファイル 1 行
```

Python の標準ライブラリだけで動きます。エンジンも PIL も、インストールも要りません。

## 判定のしかた

接空間のノーマルマップは、面の傾きを描いた絵です。赤が横方向の傾き、緑が縦方向の傾き。緑を
どちらの符号で読むかで、傾きの場の候補が 2 つできます。

**実在する面の傾きになれるのは、そのうち 1 つだけです。**本物の傾きの場には回転(curl)がありません。
1 画素下へ進んだときの横の傾きの変化と、1 画素横へ進んだときの縦の傾きの変化は、同じ量になります。
緑を正しい符号で読むと、この 2 つの混合差分が画素ごとに一致します。逆の符号で読むと、大きさが
同じで向きが反対になります。道具は内側の全画素でこの 2 つを計算し、どちらの符号で一致するかと、
それぞれの読み方で残る回転の量を出します。

```
Y-   Twill_normal.png   agreement -1.000  z -360.6  curl if Y+ 2.000 / if Y- 0.000
```

`curl if Y+` は、完全な Y+ のマップなら 0、完全な Y− のマップを逆に読んだら 2 になります。

この判定には、**縦と横の両方向に同時に曲がる凹凸**が要ります。**ストライプ・平らなマップ・ただの
雑音にはそれが無いので、答えは理由つきの `undecided`(判定不能)で、推測はしません。**判定を出すのは、
一致の度合い(agreement)の大きさが 0.25 以上で、**かつ** 0 から標準誤差 6 つ分以上離れているとき
だけです。

## 答えを知っているマップで測った

| マップ | 結果 |
|---|---|
| **09-13 に配った版の布地**(11 枚・512×512) | **Y− 10 枚、判定不能 1 枚**(ストライプ) |
| 09-17 に直した版の同じ布地 | **Y+ 10 枚、判定不能 1 枚**(ストライプ) |
| 当店の生成器が作るそれ以外のノーマルマップ全部(生成器 10 本から 65 枚: 布地・床・金属・液体・自然物・SF・お菓子・生きもの・和室・ニット。512×512) | **Y+ 64 枚、判定不能 1 枚**(ここでもストライプ)、**Y− 0 枚** |
| ……同じ 65 枚の緑を反転したもの | **Y− 64 枚、判定不能 1 枚、Y+ 0 枚** |
| 時間 | 65 枚で **7.4 秒**(512×512 1 枚あたり約 0.1 秒) |

**どの行でも、逆の答えを出したマップは 1 枚もありません。**棚の中で一致の度合いがいちばん低かった
のは +0.68(ヘアライン金属。細い筋が一部の画素を 8 bit の端まで押している)で、残りはすべて +0.82
を超えていました。

**この表のいちばん弱いところは、全部が自分たちの物だということです。**上のマップはどれも同じ 1 つの
関数 —— 中心差分。この道具自身が使うのと同じ微分 —— から出ているので、合って当然です。試験では
別の 3 通りの作り方(Sobel フィルタ、前進差分、差分を一切使わない解析的な法線)も確かめていて、
3 通りとも両方向で正しく判定されます。**それでも、Substance・Blender・xNormal・フォトグラメトリで
焼いたマップには、まだ 1 枚も当てていません。**当ててくださったなら、その 1 行は上の表全部より
価値があります。

## できないこと

- **緑を赤との関係で測っています。**赤が右向き(+X)であることを前提にしていて、これは 2 つの流儀で
  共通です。**赤と緑の両方**が反転したマップは Y+ と読まれます。それは別の不具合で、この道具には
  見えません。
- **接空間のマップ専用です。**オブジェクト空間・ワールド空間のノーマルマップは傾きの絵ではなく、
  それに何を出すかは試していません。出た答えに意味はありません。
- **一方向にしか変わらない凹凸は、難しいのではなく判定できません。**まっすぐなストライプ、まっすぐな
  1 本の稜線。同じストライプでも軸から傾ければ(試験では 45°)判定できるようになります。
- **手描きや大きく手を加えたマップ**は、傾きの場になっていないことがあります。両方の読み方が
  どちらも合わないとして `undecided` になることがあり、それはそのマップにとって正しい答えです。
- **PNG だけ**です。8/16 bit、RGB/RGBA、インタレースなし。青がちょうど 0 のチャンネルは「空」と
  みなし、単位長から作り直します(2 チャンネルのマップ向け)。「AG」詰め(DXT5nm のように X を
  アルファに入れる形)は読めません。
- どのエンジンを使っているかは分かりませんし、何も直しません。Y+ のエンジンで Y− のマップを使う
  には、緑を反転してください: `G → 255 − G`。

## 試験

```bash
python -m unittest test_normal_y_check -v
python mutation_check.py
```

**試験は 35 本。`mutation_check.py` が道具を 1 行ずつ 21 通りにわざと壊し、21 通りとも試験に
捕まります。**その 1 本目は、この道具の存在理由そのもの —— 判定を入れ替えて「一致したら Y−」に
する —— で、他の何を信じるよりも先に、これが落ちるのを見ました。

**最初の実行で捕まったのは 21 通り中 19 通り**でした。生き残った 2 通りはどちらも等価な変異では
なく、試験の本当の穴でした。

1. **有意性の下限を外す。**何も気づきませんでした。96×96 の雑音では、一致度の下限だけで止まって
   いたからです。8×8 の小片では止まりません。画素が数十個なら、偶然 0.25 を超える一致はたやすく
   起きます。いまは 60 個の小さな雑音の小片すべてが `undecided` になることを試験が求めます。
2. **16 bit の値を 8 bit の尺度で読む。**これも気づきませんでした。`赤 / 青` の比はこの誤りを
   ほぼそのまま通り抜けるので、**判定は間違った理由で正しく出ていた**のです。壊れるのは「そもそも
   ノーマルマップか」の検査のほうでした。いまは 16 bit の色のテクスチャを渡し、断られることを
   試験が求めます。

試験側の PNG 書き出しは、フィルタも Paeth 予測子も RFC 2083 から自前で持っています。道具の
読み取りを壊しても、書き出しが同じように壊れることはありません(以前 [`tile-seam/`](../tile-seam/)
で一度やった誤りです)。

## ご自分のマップに当ててみたら

**面白いのは、この道具が間違えたときです** —— Y+ だと分かっているマップが Y− と出た、よく作られた
マップが `undecided` と出た、など。`--tsv` の行と、マップの出どころ(どのベイカー・どの設定)を
[Issue](https://github.com/samuboon/claude-code-harness/issues/new) に貼ってください。行に入るのは数字と
ファイル名だけで、画像のデータは入りません。
