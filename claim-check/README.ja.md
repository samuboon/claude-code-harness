# claim-check —— milvus#27468 は「この課題をやりたいです」と言った人に 631 日割り当てられたままで、その後 2 人が「やらせてほしい」と頼んでいる

`milvus-io/milvus#27468`(「Improve milvus cli」)には `good first issue` のラベルが付いています。
2024-12-31 に、ある人が *「誰も取り組んでいないなら、この課題をやりたいです」* と書き、27 分後にメンテナが
`/assign @… please help on it` と返しました。その人の言葉はそれが最後です。2026-05-28 に別の人が
*「やってみてもいいですか?」*、2026-06-24 にさらに別の人が *「自分か前の人に割り当てるか、閉じてください」*
と頼みましたが、どちらにも返事はありません。この課題にはもう 1 人割り当てられている人がいて、その人も
2024 年 7 月に「やりたい」と書いたきりです。

名乗りには期限がありません。割り当てられた課題は `no:assignee` の一覧 —— 手の空いた人が空いている課題を
探す絞り込み —— から消えます。放置を拾うボットは「最後に何かあってからの日数」を数えますが、
「やらせてもらえますか?」も「何か」なので、新しく名乗る人が来るたびに時計が戻ります。名乗りが死んでいると
分かるのは、スレッドを最後まで読んだ人だけです。

`claim_check.py` はそれを読みます。未完了の課題で名乗った人 —— *"I'd like to work on this"*・
*"can I take this?"*・*"please assign it to me"*・`/assign`・*"I'll look into it"* —— の 1 人ずつに、
一つだけ問います。**その人は、その後この課題で何かしたか。**

```bash
python claim_check.py OWNER/NAME                     # 未完了の課題すべて
python claim_check.py OWNER/NAME --label "good first issue"
python claim_check.py OWNER/NAME --days 60           # 30 日ではなく 60 日黙っていたら
python claim_check.py OWNER/NAME --as-of 2026-03-24  # その日の状態で判定する
python claim_check.py OWNER/NAME --json
```

2026-09-24 に鍵なしで実際に走らせた結果です(ここでは利用者名を `@…` に置き換えています。道具は名前を出します):


名乗りの文は、道具が読んだ形(小文字にし、引用・コード・メンションを外したもの)で出ます。最後の修正の前の版は
#6881 を `UNANSWERED` と出していました。名乗りが問いの形で終わっていて、割り当てをその答えとして数えていなかったためです。

標準ライブラリのみ。読むだけで、コメントも割り当てもラベル付けもしません。`GONE` があれば終了コード 1、
無ければ 0、**リポジトリか課題の履歴が読めなければ 2** —— 何も読めなかった検査が「問題なし」を出してはいけないからです。

## 何を出すか

| 印 | 重さ | 意味 |
|---|---|---|
| `GONE` | error | 今もその人に割り当てられていて、その後その人から何も無い。誰かが気づくまで `no:assignee` の一覧に出ない |
| `QUIET` | warning | 割り当ては無い。メンテナが返事をした(か本人がメンテナ)のに、その後本人から何も無い。返事が「まだ待って」「これではない」だったことも多いので、読んでください |
| `UNANSWERED` | warning | 名乗ったのにプロジェクトの誰も返事をしていない —— または本人の最後の言葉が、誰も答えていない問いだった。黙っているのはプロジェクトの側かもしれない |
| `UNCHECKED` | warning | 課題の履歴が読めず、名乗りを判定していない |

名乗りが**終わる**のは、本人がやり遂げたとき(課題を結ぶか名指す本人の PR)、手放したとき
(*「もう時間が取れません。どなたかどうぞ」*)、プロジェクトが次へ進んだとき(本人の割り当てを外した・
別の人を割り当てた・別の人の PR が課題を結ぶか名指した)です。本人の後のコメント・コミット・相互参照は時計を戻します。
他の人が持っている課題に名乗り、その人が今も持っているものは出しません。引用行(`>`)・コード・HTML コメント・
`/assign @別の人` は名乗りとして読みません。ボットと、他の管理ツールからの転記用アカウント(`jenkins-infra-bot`・
`swift-ci`)も読みません。各行には、本人が黙ってから何人が「やらせてほしい」と言ったかが付きます。

**履歴に出ない PR。** 所見ごとに 2 回検索します —— 名乗った日以降に本人がそのリポジトリで開いた PR と、
課題の番号を含む PR。どちらかが課題を名指していれば(`#N` か URL)、その所見は出しません。鍵があるときは、
GraphQL から課題ごとの「閉じる PR」も読みます。理由は下にあります。

## 正しいとどうして分かるか

すべて 2026-09-24 の実測です。`good first issue` が 10 件以上あり star が 5,000 以上のリポジトリ 333 本を取り、
**道具をどれかに合わせて直す前に、名前の hash で半分に分けました。**それぞれについて、コメントに名乗りらしい語を
含む未完了の課題を集めました(検索 5 本、各 100 件まで)。直すのには片方の半分(164 本)だけを使いました。
もう半分からは、star の多い 80 本で第 1 版を測りました(その日読めたのは 79 本)。その 80 本の外れを読んで
道具を直したので、**最終版は、どの版も一度も当てていない残りの 83 本で測りました**(先に少し目に触れた 6 本は外しました)。

| | 第 1 版 · 取っておいた 79 本 | 最終版 · 未見の 83 本 |
|---|---:|---:|
| 読んだ未完了の課題 | 16,849 | 13,844 |
| 履歴だけで出た `GONE` | 1,293 | 252 |
| …無作為に抜いた / 検索の後に残った / **本物** | 320 / 185 / **95 (51%)** | 228 / 150 / **103 (69%)** |
| 履歴だけで出た `QUIET` | — | 662 |
| …抜いた / 残った / **本物** | — | 92 / 60 / **30 (50%)** |
| 履歴だけで出た `UNANSWERED` | 1,729 | 1,315 |
| …抜いた / 残った / **本物** | 160 / 89 / **69 (78%)** | 80 / 60 / **43 (72%)** |

「検索の後に残った」ものが、道具が実際に出す所見です。残りは、課題を名指す PR が見つかって外れました
(第 1 版の標本では、まだ閉じる PR を読んでいなかったので、それで外れたものも含みます —— 320 件中 105 件)。
**検索は、履歴だけで出る所見の 4 分の 1 から 3 分の 1 を落とします** —— 未見の 83 本で `GONE` 228 件中 78、
`QUIET` 92 件中 32、`UNANSWERED` 80 件中 20。

「本物」は、名乗り・その後の履歴すべて・本人がその後そのリポジトリで開いた PR の題を見た判定者の判定です。
条件は、その課題への名乗りであること、やり遂げた跡が無いこと、名乗りが意味を失った跡が無いこと(断られた・
もう直っている・別の人に渡った・取り下げた)、そして `GONE` と `QUIET` では、黙っているのが本人の側であること
(答えの無い問いを残したのは本人ではない)。判定者は、この条件と記録だけを渡した別のモデルのセッションで、
道具のコードは見ていません。判定 569 件すべて —— リポジトリ・課題・印・判定・理由の種類 —— を
[`judged.tsv`](judged.tsv) に置きました(利用者名は入れていません)。

**第 1 版の `GONE` は半分外れていました。** 185 件中、本物は 95 件です。第 1 版は、メンテナが返事をしていれば
`GONE` にしていましたが、その返事はしばしば *「新しい人は 1 人 1 件まで」「先に設計を決める必要がある」
「もう直っている」* で(断り・意味を失ったものが 25 件)、あるいは誰も答えない問い返し(15 件)、
あるいは別の人がもう取り組んでいた(15 件)でした。第 1 版の `GONE` のうち、今も本人に割り当てられているものは
66% が本物(80 件中 53)、「メンテナが返事をした」ものは 38%(94 件中 36)。これが最終版の分け方です ——
割り当てられているものが `GONE`、残りが `QUIET` です。

**未見の 83 本で、最終版の `GONE` は 69% が本物でした(150 件中 103)。**外れた 47 件のうち 21 件は、
課題を名指さずに中身をやっている PR を本人が出していたもの —— 行に *「N other pull requests from them here
since」* と出るので、見るのはそこです —— 14 件は、本人がプロジェクトを待っていたもの(依存の取り込み・
やり方のレビュー・方針の決定)で、道具が「答えの無い問い」とは読まない言い方でした。`QUIET` は五分五分
(60 件中 30)で、だから warning です。メンテナの返事は「まだ待って」であることが多いのです。

この測定の後に 2 つ直しました。どちらも 1 つの課題を最後まで読んで見つけたものです。`/assign @誰か`
(メンテナが別の人を割り当てる)をメンテナ自身の名乗りと読まなくしたことと、割り当てられたことを
「やらせてもらえますか?」への答えとして数えるようにしたことです。未見の 83 本では 2 つ目で 35 件が
`UNANSWERED` から `GONE` に移り(1 件は消える)、その 35 件を抜いて検索の後に残った 25 件を判定すると
**21 件が本物(84%)**でした。公開版はそこで検索の前に **`GONE` を 287 件**出します。2 つの標本を重みづけると、
`GONE` として出るもののおよそ 71% が本物です。

### 鍵が PR をすべて隠すことがある

最初に測ったものは間違っていました。そのリポジトリを許可していない fine-grained の鍵で履歴を読むと、
**相互参照が 1 件も返りませんでした** —— 206 本のリポジトリの 41,780 課題で、相互参照の出来事は 0 件
(手で「connected」した PR 515 件は返りました)。同じ問い合わせを鍵なしで行うと出ます —— `apache/airflow#9186` には
鍵なしなら相互参照された PR が 2 本あり、その鍵では 0 本です。つまり道具は、やり遂げた仕事を放置と呼んでいました。
そういう鍵でも GraphQL の `closedByPullRequestsReferences`(「fixes #N」と書いた PR)は読めます。これを足すと、
取っておいた 80 本で第 1 版の **`GONE` 2,016 件のうち 716 件(36%)、`UNANSWERED` 2,851 件のうち 1,110 件(39%)**
が消えました。それでも補えないのは、「fixes」と書かずに課題を名指す PR —— 2 つの検索はそのためにあります ——
と、別のリポジトリの PR です。鍵なしで読み直した 4 例のうち 2 つがそれぞれを示しています。`recharts/recharts#4438` は
2024 年 4 月から黙っている人に今も割り当てられていますが、2026 年 8 月にメンテナが別の人に *「Go for it」* と言い、
その人の PR 3 本が課題を名指しています。鍵つきで読んだ履歴にはそのどれも出ず、番号の検索は 3 本とも見つけ、
所見は外れます。`apache/dubbo#13861` では、名乗った人が 5 日後に `apache/dubbo-samples#1132` —— 別のリポジトリの
PR —— を開いていて、鍵つきの道具はそれを今も出します(*「47 other pull requests from them here since」* が付くので、
見るべきだと分かります)。

道具は今、これが起きたら言います。閉じる PR を持つ課題があるのに、どの履歴にも相互参照が 1 件も無ければ、
その鍵には見えていないと出します。

### 半年後

`--as-of 2026-03-24` は、課題をその日の状態で判定します。最終版をそうやって取っておいた 80 本に当て
(2026-03-24 に開いていた課題。その後閉じたものも含む)、その後の半年で何が起きたかを見ました ——
名乗った本人が戻ってきたか(コメント・コミット・課題を結ぶか名指す PR)。

| 2026-03-24 の時点で黙っていた日数 | 名乗り | 2026-09-24 までに本人が戻った |
|---|---:|---:|
| 0〜6 日 | 74 | 20 (27%) |
| 7〜13 日 | 52 | 13 (25%) |
| 14〜29 日 | 125 | 19 (15%) |
| 30〜59 日 | 178 | 13 (7.3%) |
| 60〜89 日 | 166 | 4 (2.4%) |
| 90〜179 日 | 426 | 13 (3.1%) |
| 180〜364 日 | 337 | 11 (3.3%) |
| 1 年以上 | 1,594 | 23 (1.4%) |

上の 3 行は道具が出さない名乗り、残りは出す名乗りです。その日に開いていた名乗り 2,952 件すべてを、履歴だけで
数えています。**黙って 30 日未満なら、半年のうちに 5 人に 1 人が戻りました。30 日を過ぎると 42 人に 1 人
(2,701 件中 64 件)です。**このうち 663 件(第 1 版で 30 日未満だったものすべてと、残りから無作為に 400 件)に
2 つの PR 検索も当て、その時点で PR が課題を名指していたものを外すと、30 日未満は 199 件中 37 件(19%)、
30 日以上は 326 件中 9 件(2.8%)が戻りました —— 割り当てられたままの 52 件中 6 件、`QUIET` の 91 件中 0 件、
`UNANSWERED` の 183 件中 3 件です。

### 人が手でやった同じ検査

同じ検査は、人が 1 件ずつ手でやっています —— *「@誰か、まだやっていますか?」*。取っておいた 80 本で、前にコメントした
人を名指すそういうコメントが 344 件ありました。それぞれが書かれた瞬間に、道具はその人の名乗りを **173 件(50%)**で
開いたまま持っていました。残り 171 件のうち 117 件は、名乗りの文を一度も書いていない人 —— 直接割り当てられた人か、
PR の書き手 —— への問いで、残りは、道具が既に閉じていた名乗り(PR・引き継ぎ・他の人が持っている課題)でした。

人は早めに聞いていました。聞かれた時点で本人が黙っていた日数の中央値は **19 日**、30 日以上は 173 件中 64 件(37%)で、
その 64 件については、30 日の検査なら人が聞くより中央値で 60 日早く一覧に出せていました。**そして、早いうちなら
聞けば答えが返ります。** 本人が 30 日以内に答えたのは、最後の言葉から 2 週間以内に聞かれたとき 78%(77 件中 60)、
14〜29 日で 72%(32 件中 23)、30〜89 日で 70%(30 件中 21)、**90 日を過ぎると 38%(34 件中 13)**でした。これは
誰かが気にかけて聞いた名乗りの数字で、上の半年の表はすべての名乗りの数字です。聞いたから答えが返ったとは主張しません。

## やらないこと

- **英語だけ。**他の言語の名乗りは読みません
- **言葉の無い名乗りは読みません。**何も言わずに割り当てられた人は、ここでは名乗った人ではありません。割り当てから N 日で
  外すアクションがその場合を扱っています
- **割り当てが 2 人。**本人の後に別の人が割り当てられると、本人が割り当てに残っていても、名乗りは引き継がれたものとして扱います。
  `milvus#27468` の 1 人目が出ないのはこのためです
- **別のリポジトリの PR** は、鍵が相互参照を隠しているときは見えません(上の `apache/dubbo#13861`)。鍵なしなら履歴に出るので読みます
- **課題を名指さずに中身をやっている PR** は、黙っていると数えます。行に、本人がその後そのリポジトリで開いた PR の数が出るので、
  見られます。最終版の未見の標本では `GONE` 150 件中 21 件がこれでした
- **メンテナの返事の意味は読みません。**だから `QUIET` は warning です
- **誰にも何も聞きません。**出るのは、聞くべき人の一覧です
- 所見ごとに 2 回検索します。鍵があれば GitHub は 1 分 30 回、無ければ 10 回まで許します(`--no-search` で飛ばせますが、
  そのぶん PR の確かめも飛びます)

## CI で

```yaml
on:
  schedule: [{cron: "0 6 * * 1"}]
jobs:
  claims:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python tools/claim_check.py ${{ github.repository }} --label "good first issue"
        env:
          GITHUB_TOKEN: ${{ github.token }}
```

`claim_check.py` は 1 ファイルです。`run:` の行が指す場所に写してください。私たちは GitHub Actions でこれを走らせておらず、
その鍵に相互参照が見えるかも知りません —— 見えなければ、道具がそう言います。

## 試験

`python test_claim_check.py` —— 試験 44 本。`python mutation_check.py` は道具を 47 通りに 1 つずつわざと壊し、試験が
気づかなければ失敗します。**47 通りすべてを捕まえます。初回は 35 通り中 33。**`"I don’t think I can take this on"` の
活字のアポストロフィが見逃され、もう 1 つはどんな結果も変えられない壊し方でした —— それを置き換える試験を書いたら、
本物の誤りが見つかりました(本人の最後の言葉より前に「やらせてほしい」と言った人を、黙ってから言った人として数えていた)。
