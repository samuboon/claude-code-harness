# prose-expiry —— 誰かが一度だけ文章に書いた、それきり誰も読み返さない期日

隣にある [`key-expiry/`](../key-expiry/) は、自分の死ぬ日を自分の中に持っている資格情報 2 種類(JWT の `exp`、X.509 の `notAfter`)を読み、**それ以外については何も言えない**と正直に書いて終わります。

**この道具はその「それ以外」です。**サポート終了。契約の更新日。移行の締切。他人が持っている証明書の期限。試用が請求に変わる日。実際にチームが抱えている期日のほとんどは、README か課題票か表のセルか定数の上のコメントに、**一度だけ文章として書かれ、その日を過ぎても誰もその文章を読み返しません。**

```bash
python prose-expiry/prose_expiry.py .                    # 木ぜんぶ
python prose-expiry/prose_expiry.py . --within 30
python prose-expiry/prose_expiry.py . --format paste     # 件数だけ。パスも本文も出さない
python prose-expiry/prose_expiry.py . --ledger EXPIRY.tsv
```

このリポジトリ自身に当てた 2026-09-16 の実測(この道具の試験用ファイルは除外):

```
6 written expiry dates over 3 distinct dates in 58 files, read on 2026-09-16
  already passed : 0
  within 90      : 6
  later          : 0
  weak cues not counted: 5  (--include-weak to see them)
  a date nobody wrote down is not here. That is what EXPIRY.tsv is for.
```

6 行を読むのに 1 分かかりません。そのうち 1 行 —— `pjo-exit-check/README.ja.md:5` の「Project Online は 2026-09-30 で提供終了します」—— は本物の期日で、その日が来たらこのリポジトリの中の 1 フォルダは値打ちを失います。

---

## この道具が間違えた 3 つ(このリポジトリでの実測)

**1. 既定の幅では、このリポジトリが作られた理由そのものの期日を取り落としました。**英語側のファイルにはこう書いてあります。

```
Project Online retirement : 9/30/2026 8:00:00 AM Pacific Time (= 2026-09-30 15:00 UTC)
```

*retirement* という語と ISO の日付のあいだが 50 文字あり、既定の `--near 40` は繋ぎません。日付の隣に「提供終了」と書いてある日本語側は拾えています。`--near 80` にすると両方拾い、件数は 6 行から 9 行になります。**自分の作者のファイルで出した取り落としを自分で報告する道具のほうが、しない道具より役に立つ**ので、これを脚注ではなく最初の節に置きました。

**2. 文章の多い木では雑音が多く、これは語彙を増やしても直りません。**このリポジトリを生んでいる非公開の作業木は、**期日そのものを主題にした**日本語の文書 677 ファイルです。結果:

```
985 rows over 124 distinct dates
  already passed : 276  (oldest by 17539 days)
```

いちばん古い行は 1978 年でした —— 2026 年に閉店する店の話の中で、30 文字離れたところに開業日の 1978 年が書いてある文です。「満了」はその文にありますが、別の日付についての語でした。この木では `--near 12` が 985 行を 602 行に落とし、本物は落ちません。残り半分の答えは `--exclude` です。**正直に言えば、日付を常に語っている木の上では語彙による判別の精度は低く、どう調整しても良くはなりません。**

**3. 誰も書き留めなかった期日は、ここには出てきません。**これはどの版でも直らない限界で、[`EXPIRY.tsv`](EXPIRY.tsv) が在る理由そのものです —— 頭の中と誰かの受信箱にしか無い期日のための、空の 5 列。

```
kind    date    what_stops    how_you_found_out    days_late
（種別  期日    切れたら止まるもの  気づいた経路  遅れた日数）
```

`--ledger EXPIRY.tsv` を付けると、その行が走査の結果と同じ表に並びます。4 列目と 5 列目は飾りではありません。**「どうやって気づいたか」と「何日遅れたか」は、その期日が問題なのか不便なだけなのかを分ける唯一の 2 つの事実**で、しかも誰も記録していない 2 つです。

## 日付が 1 行になる条件

1. 本物の暦の日付が行にある(`2026-09-30` / `2026年9月30日` / `September 30, 2026` / `30 Sep 2026`)。`2026-02-30` は日付ではなく、`2026-09/30` も違います。
2. **期限の合図**が、同じ行の `--near` 文字以内か、5 行上までの見出しにある。強い合図は、文脈なしでも読者が納得する語です(`EOL` / `end of support` / `expires` / `deadline` / `sunset` / `deprecated` / `retire` / `valid until` / `期限` / `提供終了` / `失効`)。弱い合図(`due` / `until` / `renew` / `更新` / `移行`)は**数えて最後に件数だけ出し、行にはしません** —— 変更履歴が過去について使う頻度と、計画が未来について使う頻度が変わらないからです。`--include-weak` で昇格します。
3. **どの行にも、当たった合図の名前が入ります。**なぜこの道具が期日だと思ったのかが見えるので、読む側が覆せます。

| 旗 | 何のためか |
|---|---|
| `--within N` | 窓(既定 90 日) |
| `--near N` | 合図と日付の近さ(既定 40 文字) |
| `--include-weak` | `due` / `renew` / `更新` の類も行にする |
| `--exclude GLOB` | パスを除く(繰り返し可。例 `--exclude 'test_*'`) |
| `--ledger FILE` | どのファイルにも書かれていない期日を足す |
| `--today YYYY-MM-DD` | 「あの日には何が過ぎていたか」を訊く |
| `--format tsv\|paste\|github` | 表 / パス無しの件数 / `::warning` 注釈 |

戻り値: **0** = 過ぎたものも窓の中のものも無い・**1** = ある・**2** = 走査が成立しなかった。**0 ファイルしか読めなかったときは 2 で終わります** —— 空の走査に緑の印を出すのは、エラーで止まるより悪いからです。

```yaml
- run: python prose-expiry/prose_expiry.py . --within 30 --format github
```

## しないこと

通信しません。標準ライブラリ以外を使いません。人が文章を書くファイルしか開かず、`.env` `.pem` `.key` `id_rsa` の類は開きません。行を出す前に、パスではなく資格情報に見える 24 文字以上の連なりを伏せます。`--format paste` はさらに進んで、**本文もファイル名も一切出しません** —— その塊はそのまま公開の場所に貼れます。

## 使わなくていい人

期日が既にカレンダー・期限付きの課題管理・誰かが持っている更新表に入っているなら、この道具に用はありません。**他に置き場が無かったから文章の中に書かれた期日**のための道具です。

## 試験

```bash
python -m unittest discover -s prose-expiry -p "test_*.py"   # 50 本
python prose-expiry/mutation_check.py                        # 変異 18 本、全部捕捉
```

`mutation_check.py` は道具を 18 通りにわざと壊し(日を月として読む・近接の条件を外す・何も読めなかった走査に緑の印を出す・`--format paste` に本文を出させる)、試験が 1 つでも見逃したら赤で終わります。**初回は 18 本中 2 本が生き残りました。**それを捕まえる試験が `Cues` と `Ledger` に増えています。
